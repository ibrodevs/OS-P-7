Работа реализована на Python 3 с использованием стандартных механизмов IPC: именованных каналов FIFO, Unix domain sockets, `multiprocessing.Pipe` и `multiprocessing.shared_memory`. ## Выполнение задания

### 1. Клиент–сервер на FIFO

Сервер создаёт общий FIFO `/tmp/ipc_calc_requests` и последовательно читает запросы клиентов.

Каждый клиент создаёт собственный FIFO вида:

```text
/tmp/ipc_calc_response_<pid>_<uuid>
```

В запросе передаются выражение и путь к обратному FIFO. Сервер вычисляет результат и записывает ответ именно в FIFO этого клиента.

Такая схема позволяет нескольким клиентам пользоваться одним сервером по очереди, не смешивая ответы.

### 2. Почему FIFO может блокироваться

Операция открытия FIFO на запись может ждать, пока другой процесс не откроет канал на чтение. Аналогично читатель может ждать писателя.

Это нормальное поведение именованных каналов и одна из причин, почему при работе с FIFO особенно важно понимать порядок открытия концов канала.

### 3. Unix domain sockets

Второй вариант сервиса использует:

```python
socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
```

Сервер принимает подключения через `accept()` и создаёт отдельный `multiprocessing.Process` для каждого клиента.

В отличие от последовательного FIFO-сервера, несколько socket-клиентов могут обслуживаться одновременно.

### 4. Безопасное вычисление выражений

Для калькулятора не используется прямой `eval()`. Арифметическое выражение разбирается через AST и разрешён только ограниченный набор математических операций.

Это предотвращает выполнение произвольного Python-кода через клиентский запрос.

### 5. SharedMemory против Pipe

`benchmark_ipc.py` создаёт массив из **10 000 000** 32-битных беззнаковых чисел. Полезная нагрузка составляет примерно **38.15 MiB**.

При SharedMemory:

1. родитель создаёт общий сегмент памяти;
2. записывает туда массив;
3. ребёнку передаётся имя сегмента;
4. ребёнок читает данные непосредственно из общей памяти.

При Pipe массив сериализуется в байты и передаётся через межпроцессный канал.

### 6. Результаты измерения

В контрольном запуске получено:

```text
SharedMemory: 0.021796 s
Pipe:         0.110820 s
Pipe / SharedMemory: 5.08x
```

В данном эксперименте Pipe оказался примерно в **5.08 раза медленнее**.

Причина — через Pipe требуется фактически передать весь объём данных между процессами, тогда как shared memory позволяет обоим процессам обращаться к общей области памяти.

### 7. Очистка ресурсов

После завершения программы:

- сервер удаляет созданный FIFO;
- клиент удаляет свой обратный FIFO;
- Unix-сервер удаляет socket-файл;
- shared memory закрывается и вызывается `unlink()`.

Это выполняет требование, что после завершения не должны оставаться разделяемые ресурсы.

## Сравнение механизмов

| Механизм | Синхронизация со стороны программиста | Типичный объём | Особенности |
|---|---|---|---|
| FIFO | нужна координация чтения/записи | сообщения/поток байтов | прост, но блокируется при открытии сторон |
| Unix socket | протокол обмена задаёт программа | сообщения/поток | удобен для клиент–серверной модели |
| Pipe | частично скрыта API | средние объёмы | данные копируются через канал |
| SharedMemory | **обязательна при совместной записи** | большие объёмы | очень быстро, но опаснее из-за общей памяти |

## Ответы на контрольные вопросы

### Почему shared memory самая быстрая и самая опасная?

Она быстрая, потому что процессы могут обращаться к одной области памяти без передачи каждой порции данных через отдельный IPC-канал. Опасность состоит в том, что несинхронизированные чтение и запись могут привести к race condition и повреждению общего состояния.

### Что произойдёт при записи в pipe без читателей?

Если все читающие концы закрыты, запись в pipe приводит к сигналу `SIGPIPE`; если сигнал игнорируется или обрабатывается, системный вызов записи возвращает ошибку `EPIPE`.

## Вывод

Разные IPC-механизмы подходят для разных задач. FIFO удобен для простого последовательного обмена, Unix sockets — для полноценной клиент–серверной модели, Pipe — для прямой передачи данных между связанными процессами, а shared memory особенно эффективна для больших объёмов. При этом повышение производительности shared memory требует большей ответственности за синхронизацию и очистку ресурсов.
