# Практическая работа № 7 — Межпроцессное взаимодействие

**Вариант B**

Цель работы: организовать обмен данными между процессами через FIFO, Unix domain sockets, `multiprocessing.shared_memory` и `Pipe`, а затем сравнить механизмы IPC.

## Состав проекта

- `calc_common.py` — безопасный вычислитель арифметических выражений.
- `fifo_server.py` — сервер-калькулятор на именованном канале FIFO.
- `fifo_client.py` — клиент FIFO; для ответа создаёт отдельный FIFO.
- `unix_server.py` — сервер на `socket.AF_UNIX`; каждый клиент обслуживается отдельным процессом.
- `unix_client.py` — клиент Unix-сокета.
- `benchmark_ipc.py` — передача массива из `10^7` чисел через SharedMemory и Pipe и сравнение времени.

Для работы достаточно Python 3.8+ на Linux/macOS. Сторонние библиотеки не нужны.

---

## 1. Клиент–сервер на именованных каналах

Сервер использует общий FIFO `/tmp/ipc_calc_requests` для запросов. Каждый клиент создаёт свой FIFO вида `/tmp/ipc_calc_response_<pid>_<uuid>`, передаёт его имя серверу вместе с выражением, получает ответ и удаляет свой FIFO.

Сервер обрабатывает запросы последовательно, поэтому несколько клиентов могут обращаться к нему по очереди.

### Терминал 1 — сервер

```bash
python3 fifo_server.py
```

### Терминал 2 — клиент

```bash
python3 fifo_client.py "(10 + 2) * 3"
python3 fifo_client.py "100 / 4 + 7"
python3 fifo_client.py "2 ** 10"
```

Пример:

```text
Result: 36
Result: 32.0
Result: 1024
```

Остановка сервера: `Ctrl+C`. Сервер удаляет `/tmp/ipc_calc_requests`, а клиент удаляет свой FIFO в блоке `finally`.

> Важно: обычный FIFO может блокироваться на `open()`, пока противоположная сторона не откроет канал. Это нормальное поведение именованных каналов.

---

## 2. Тот же сервис на Unix domain socket

Используется `socket.AF_UNIX` и файл сокета `/tmp/ipc_calc.sock`. После `accept()` сервер запускает отдельный `multiprocessing.Process` для каждого клиента, поэтому запросы могут выполняться одновременно.

### Терминал 1 — сервер

```bash
python3 unix_server.py
```

### Терминал 2 — один клиент

```bash
python3 unix_client.py "7 * 8 + 1"
```

### Несколько клиентов одновременно

```bash
python3 unix_client.py "1 + 2" &
python3 unix_client.py "10 * 10" &
python3 unix_client.py "144 / 12" &
wait
```

Остановка сервера: `Ctrl+C`. Файл `/tmp/ipc_calc.sock` удаляется при завершении.

---

## 3. SharedMemory против Pipe

`benchmark_ipc.py` создаёт массив из **10 000 000** беззнаковых 32-битных чисел. Размер полезной нагрузки составляет примерно **38.15 MiB**.

Для SharedMemory родительский процесс создаёт общий сегмент, записывает туда массив и передаёт дочернему процессу только имя сегмента. Для Pipe байты массива проходят через канал между процессами.

Запуск:

```bash
python3 benchmark_ipc.py
```

Для быстрого теста можно уменьшить размер:

```bash
python3 benchmark_ipc.py --count 100000
```

Скрипт проверяет первое, среднее и последнее значения, печатает время обоих способов и всегда вызывает `shm.unlink()` в `finally`, поэтому сегмент разделяемой памяти не должен оставаться в `/dev/shm`.

## 4. Сравнение IPC

| Механизм | Нужна ли синхронизация со стороны программиста | Объём данных в этой работе | Время передачи / характеристика |
|---|---|---:|---|
| FIFO | Да: нужно согласовать чтение/запись и порядок запрос–ответ | Малые сообщения, обычно меньше 1 KiB | Низкая задержка локально, но операции могут блокироваться |
| Unix domain socket | Протокол запрос–ответ нужен; параллелизм организует сервер | Малые сообщения, обычно меньше 1 KiB | Низкая задержка; удобен для нескольких клиентов |
| SharedMemory | **Да, обязательно** при одновременной записи/изменении | `10^7` × 4 байта ≈ 38.15 MiB | **0.021796 s** в контрольном запуске |
| Pipe | Базовая синхронизация чтения/записи встроена, но протокол всё равно нужен | `10^7` × 4 байта ≈ 38.15 MiB | **0.110820 s** в контрольном запуске |

В контрольном запуске этой работы Pipe оказался примерно **в 5.08 раза медленнее** SharedMemory для массива `10^7` чисел. Для FIFO и Unix socket в таблице указана характеристика задержки, потому что они передают короткие запросы калькулятора, а не массив 38.15 MiB. Точное время зависит от процессора, ОС и нагрузки системы, поэтому `benchmark_ipc.py` повторно измеряет его на компьютере, где выполняется работа.

## Очистка ресурсов

После завершения можно проверить:

```bash
ls -l /tmp/ipc_calc_requests /tmp/ipc_calc.sock 2>/dev/null
ls /dev/shm | grep -i psm || true
```

При корректном завершении файлы FIFO/сокета и созданный этой программой сегмент shared memory удаляются.

## Контрольные вопросы

### 1. Почему разделяемая память — самый быстрый и самый опасный механизм IPC?

Разделяемая память быстрая, потому что после создания общего сегмента процессы работают с одной и той же областью памяти и не обязаны пересылать каждое сообщение через ядро. Для больших массивов это уменьшает количество копирований данных.

Опасность в том, что несколько процессов могут одновременно читать и изменять одни и те же данные. Без `Lock`, `Semaphore`, `Event` или другого механизма синхронизации возникают race condition, повреждение данных и трудно воспроизводимые ошибки.

### 2. Что произойдёт при записи в pipe, у которого закрыты все читающие концы?

ОС сообщает процессу об ошибке разорванного канала: на POSIX-системах процесс получает сигнал `SIGPIPE`. Если сигнал проигнорирован или перехвачен, системный вызов записи завершается ошибкой `EPIPE`. В Python это обычно проявляется как исключение `BrokenPipeError`.

---

## Вывод

FIFO прост и подходит для последовательного локального обмена. Unix domain sockets удобнее для клиент–серверного взаимодействия и нескольких одновременных клиентов. Pipe прост для родственных процессов, но большие данные приходится передавать через канал. SharedMemory лучше подходит для больших объёмов, однако требует особенно аккуратной синхронизации и обязательной очистки ресурсов.
